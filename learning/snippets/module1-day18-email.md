## The Short Version

Extended thinking and the "think" tool are two mechanisms that give Claude more reasoning budget before or during a response. They're architecturally distinct: extended thinking is a model-level parameter that generates a hidden scratchpad before every response; the think tool is an explicit tool Claude calls mid-loop to pause and reason without taking an external action. Both cost more tokens. Both improve performance on tasks where committing to a wrong first step cascades into a wrong final answer. Understanding when to use each — and when to skip both — is a practical engineering decision you'll make repeatedly when building Earnventory agents.

---

## Why Standard CoT Sometimes Isn't Enough

Chain-of-thought (Day 16) and ReAct (Day 17) both surface reasoning in the model's output. The reasoning tokens appear in the context as part of the response, constraining subsequent generation.

But standard CoT has a structural limitation: the model generates reasoning and response as a continuous sequence. The first token of the response follows immediately from the last token of the reasoning. If the task is complex enough that the model needs to fully plan before it begins the answer — to hold the whole problem in view, try approaches, discard some, then commit — standard CoT doesn't give it enough runway to do that cleanly.

Consider the difference:

```
STANDARD COT (continuous generation)
═══════════════════════════════════════════════════════════════
Reasoning token 1 → 2 → 3 ... → Response token 1 → 2 → 3 ...
         ↑
The response begins as soon as the reasoning sequence ends.
If the reasoning commits to a wrong approach, the response
follows that approach. There's no going back once token 1
of the response is generated.
═══════════════════════════════════════════════════════════════

EXTENDED THINKING (dedicated scratchpad)
═══════════════════════════════════════════════════════════════
[Hidden thinking block: explore, try, self-correct, plan]
                              ↓
                    Response token 1 → 2 → 3 ...
         ↑                            ↑
Entire thinking budget          Only committed to after
can explore and discard         the full scratchpad is done.
before committing.
═══════════════════════════════════════════════════════════════
```

In extended thinking, the model can generate a tentative answer in its scratchpad, notice it's wrong, try another approach — all before response token 1 is generated. Standard CoT doesn't allow that. Once the visible response starts, the model is committed to the direction it began.

## Extended Thinking Mode: The Architecture

Extended thinking mode is enabled via an API parameter at call time:

```python
response = anthropic.messages.create(
    model="claude-opus-4-8",
    max_tokens=16000,
    thinking={
        "type": "enabled",
        "budget_tokens": 10000   # reasoning budget before the response
    },
    messages=[{"role": "user", "content": "..."}]
)
```

When enabled, the API response includes both a `thinking` block and a `text` block:

```python
response.content = [
    ThinkingBlock(
        type="thinking",
        thinking="Let me work through this carefully. First I'll..."
        # ↑ the hidden scratchpad — available to developers, not shown to user by default
    ),
    TextBlock(
        type="text",
        text="Here is my answer..."
        # ↑ the visible response
    )
]
```

**Key architectural facts to know:**

**Budget tokens come out of max_tokens.** If you set `max_tokens: 16000` and `budget_tokens: 10000`, the model can use up to 10,000 tokens thinking and still has 6,000 for the response. If the scratchpad is shorter, unused budget is not wasted — the model stops when it's ready.

**Thinking tokens are billed as output tokens.** This is the cost reason to be deliberate about when you enable it. A 10,000-token thinking block on every call at Opus rates adds meaningful cost at scale.

**The scratchpad is not influenced by user input in the same way the response is.** The thinking block is generated by the model as an internal monologue. This provides a mild security property: the scratchpad is harder to hijack via prompt injection than the visible response.

**Extended thinking is available on Opus 4.8 and Sonnet 4.6.** Haiku does not support it — this is relevant when you're choosing model tiers for cost reasons.

**You can stream thinking blocks.** The API supports streaming extended thinking in real-time, which is useful if you want to show a "reasoning trace" to users or log it for debugging.

## The "Think" Tool: A Different Mechanism

The think tool is described in Anthropic's engineering blog and is architecturally separate from extended thinking mode. It's not a model parameter — it's an ordinary tool you define in your tools list, and Claude calls it voluntarily during an agentic loop when it judges that it needs to reason before acting.

```json
{
  "name": "think",
  "description": "Use this tool to think through a problem before taking action. The thinking will not be shown to the user but will inform your next action. Use it before any consequential tool call.",
  "input_schema": {
    "type": "object",
    "properties": {
      "thought": {
        "type": "string",
        "description": "Your internal reasoning before deciding on the next action."
      }
    },
    "required": ["thought"]
  }
}
```

When Claude calls this tool, it emits a `tool_use` block with `name: "think"` and its reasoning as the `thought` input. Your application receives this, does nothing with it (or logs it), and returns an empty or acknowledgment `tool_result`. The loop continues.

Here's what that looks like inside a ReAct loop on a real Earnventory task:

```
╔══════════════════════════════════════════════════════════════════════╗
║         THINK TOOL IN A REACT LOOP: Earnventory Reorder Task         ║
╠══════════════════════════════════════════════════════════════════════╣
║                                                                      ║
║  User: "Find the highest-margin SKU currently below reorder          ║
║         point and draft a purchase order for it."                    ║
║                                                                      ║
║  ┌─────────────────────────────────────────────────────────────┐    ║
║  │  tool_use: think                                            │    ║
║  │  thought: "Two parts: (1) find the highest-margin SKU       │    ║
║  │  below reorder — requires joining inventory levels with      │    ║
║  │  margin data; (2) draft a PO for that SKU. Margins are in   │    ║
║  │  a separate table from inventory. I'll get inventory         │    ║
║  │  below reorder first, then look up margins for those         │    ║
║  │  SKUs, then draft. Don't draft before confirming the SKU."  │    ║
║  └────────────────────────┬────────────────────────────────────┘    ║
║              (app returns empty tool_result)                         ║
║                           ↓                                          ║
║  ┌─────────────────────────────────────────────────────────────┐    ║
║  │  tool_use: get_inventory_below_reorder                      │    ║
║  │  Observe: [SKU-A (stock: 12), SKU-C (stock: 3), SKU-F (4)] │    ║
║  └────────────────────────┬────────────────────────────────────┘    ║
║                           ↓                                          ║
║  ┌─────────────────────────────────────────────────────────────┐    ║
║  │  tool_use: think                                            │    ║
║  │  thought: "Three SKUs below reorder. Now I need margins     │    ║
║  │  for all three. I'll query in a single call rather than     │    ║
║  │  one-by-one to avoid unnecessary round trips."              │    ║
║  └────────────────────────┬────────────────────────────────────┘    ║
║              (app returns empty tool_result)                         ║
║                           ↓                                          ║
║  ┌─────────────────────────────────────────────────────────────┐    ║
║  │  tool_use: get_margins(sku_ids=["SKU-A","SKU-C","SKU-F"])   │    ║
║  │  Observe: SKU-A: 18%, SKU-C: 34%, SKU-F: 22%               │    ║
║  └────────────────────────┬────────────────────────────────────┘    ║
║                           ↓                                          ║
║  ┌─────────────────────────────────────────────────────────────┐    ║
║  │  tool_use: think                                            │    ║
║  │  thought: "SKU-C has highest margin at 34% and stock of 3   │    ║
║  │  — also most critically low. Clear choice. Now draft PO."   │    ║
║  └────────────────────────┬────────────────────────────────────┘    ║
║                           ↓                                          ║
║  Final response: Draft PO for SKU-C, 50 units, [supplier], ...       ║
╚══════════════════════════════════════════════════════════════════════╝
```

**Why use the think tool instead of just implicit reasoning?**

Without the think tool, Claude's inter-action reasoning is implicit — the model reasons before each tool call, but that reasoning doesn't appear explicitly in the conversation history. It's conditioning behavior that's invisible to you. The think tool makes the reasoning **explicit and logged** as a `tool_use` block. This means:

- You can inspect what Claude was thinking before each consequential action.
- The reasoning becomes part of the conversation context, conditioning all subsequent steps more reliably.
- You have an audit trail of the agent's decision-making — invaluable for debugging production failures and for demonstrating compliance or oversight.

Anthropic's internal research (from the engineering blog) found that giving Claude the think tool improved accuracy on complex agentic benchmarks (including SWE-bench software engineering tasks) even when the tool's output was empty. The act of generating the reasoning explicitly — as a structured tool call — helped the model commit to cleaner, more traceable plans before acting.

## Comparing the Two Mechanisms

```
╔═══════════════════════════════╦══════════════════════════════════════╗
║  EXTENDED THINKING MODE       ║  THINK TOOL                          ║
╠═══════════════════════════════╬══════════════════════════════════════╣
║  API parameter (model-level)  ║  Tool you define (app-level)         ║
╠═══════════════════════════════╬══════════════════════════════════════╣
║  Hidden from user by default  ║  Visible in tool_use event logs      ║
╠═══════════════════════════════╬══════════════════════════════════════╣
║  Pre-response scratchpad      ║  Mid-loop pause between actions      ║
╠═══════════════════════════════╬══════════════════════════════════════╣
║  Happens every turn (on)      ║  Called when Claude judges it needed ║
╠═══════════════════════════════╬══════════════════════════════════════╣
║  Billed as output tokens      ║  Billed as output tokens             ║
╠═══════════════════════════════╬══════════════════════════════════════╣
║  Best for: complex Q&A,       ║  Best for: agentic loops with        ║
║  math, code generation,       ║  consequential write actions;        ║
║  ambiguous tasks where        ║  tasks needing deliberate planning   ║
║  the answer itself is hard    ║  before each external action         ║
╠═══════════════════════════════╬══════════════════════════════════════╣
║  Available: Opus 4.8,         ║  Available: any model, any tool      ║
║  Sonnet 4.6 (not Haiku)       ║  list — you define and provide it    ║
╠═══════════════════════════════╬══════════════════════════════════════╣
║  You can combine both:        ║  enable extended thinking AND        ║
║  provide the think tool in    ║  the same call for maximum           ║
║  reasoning coverage.          ║                                      ║
╚═══════════════════════════════╩══════════════════════════════════════╝
```

They're not mutually exclusive. For a high-stakes Earnventory task — say, rebalancing purchase orders across a dozen suppliers — you might want extended thinking enabled (so the initial planning pass has maximum scratchpad) AND the think tool available (so Claude explicitly reasons before each individual write action). That's belt-and-suspenders for consequential agent work.

## When Is the Token Cost Worth It?

Not every task benefits. Here's the practical breakdown:

**Definitely worth it:**
- The task requires multi-step planning where an early wrong commitment cascades (drafting a PO before confirming which SKU; allocating budget before confirming constraints).
- Complex math or logic: quarterly margin calculations, pricing optimization with multiple constraints.
- Ambiguous user instructions where the model needs to resolve ambiguity before acting — not ask for clarification, but reason through which interpretation is correct.
- Consequential write actions: `send_purchase_order`, `send_email_to_supplier`, `update_pricing`. Any tool that changes state in the real world.

**Probably not worth it:**
- Simple, deterministic lookups: "What's the current stock level for SKU-A?" The answer is the tool result; no planning needed.
- High-volume batch tasks: generating 10,000 product descriptions doesn't need extended thinking on each one. Cost scales linearly.
- Real-time conversation UI where latency is the constraint: extended thinking adds seconds. Perceptible in a chat interface.
- When you're using Haiku for cost reasons (which doesn't support extended thinking).

**Rule of thumb:** Pay the thinking budget when a human expert would pause before acting. For Earnventory, that's purchase order approval, supplier negotiation drafts, and any task where the agent has write access to external systems with real financial consequences.

## Earnventory Application

Consider an agent tasked with: *"Rebalance our open purchase orders for Q3 given the PacRim freight rate increase just announced."*

This task benefits from both mechanisms:

- **Extended thinking on the planning pass:** The agent needs to hold multiple constraints simultaneously — existing PO commitments, the new freight cost structure (12% container, 8% LTL), margin targets by SKU, and supplier lead times. That's exactly the kind of multi-constraint planning where a pre-response scratchpad helps most. You'd enable extended thinking with a generous `budget_tokens` for this initial analysis call.

- **Think tool during execution:** Once the plan is formed, the agent will execute a series of actions (modifying or canceling POs). Before each write action, having the think tool available lets it explicitly reason: "Am I about to cancel the right PO? Is this reversible? Do I have enough information?" That deliberate pause before write actions is valuable when mistakes are costly.

Contrast with a routine task like "summarize today's orders." There's no planning needed, no consequential actions, no ambiguity. Extended thinking is overhead without benefit — just call the tool, return the result.
