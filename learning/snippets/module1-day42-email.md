## The Problem: Your Code Doesn't Speak Probability

When you use Claude interactively in a chat, inconsistency is mildly annoying. When Claude's output feeds your application code — updating an Earnventory database, triggering a reorder, populating a dashboard — inconsistency is a production incident.

The core issue: Claude is a probabilistic language model. Every response is a sample from a probability distribution. Even with identical inputs, there's variance. That variance is usually fine for prose, but it's fatal for structured data.

Concretely: you ask Claude to parse a supplier invoice and return the line items. One run returns:
```json
{"items": [{"sku": "WN-001", "qty": 12, "price": 18.50}]}
```

The next run returns:
```json
{"line_items": [{"sku": "WN-001", "quantity": 12, "unit_price": 18.50}]}
```

Your code does `data["line_items"][0]["unit_price"]`. Half your runs throw a `KeyError`. The other half silently produce wrong calculations because `qty` vs. `quantity` means different things to your downstream logic.

Structured outputs are how you solve this. There are two main techniques: **strict tool schemas** and **output format prompting**. Today we cover both.

---

## Technique 1: Strict Tool Schemas

When Claude calls a tool you defined, the "arguments" Claude passes are JSON — generated by the model, not computed by your code. The question is: how tightly can you constrain what Claude is allowed to generate?

The answer is: very tightly, if you write a good schema.

Every tool definition includes an `input_schema` — a JSON Schema object describing the expected arguments. Here's a weak schema for an invoice parser:

```json
{
  "name": "parse_invoice",
  "description": "Parse a supplier invoice",
  "input_schema": {
    "type": "object",
    "properties": {
      "items": {
        "type": "array",
        "description": "Line items on the invoice"
      }
    }
  }
}
```

This schema tells Claude almost nothing. `items` can be an array of anything. There's no `required` field — Claude might omit it entirely. There's no `additionalProperties` constraint — Claude can add `notes`, `confidence`, or anything else it decides to include. The field name `items` is advisory; Claude might use `line_items` or `products` based on whatever token sequence has higher probability at that moment.

Now here's a strict schema:

```json
{
  "name": "parse_invoice",
  "description": "Parse a supplier invoice and return structured line item data for database ingestion. Every field in the schema is required.",
  "input_schema": {
    "type": "object",
    "properties": {
      "supplier_id": {
        "type": "string",
        "description": "Supplier's unique identifier as printed on the invoice header"
      },
      "invoice_date": {
        "type": "string",
        "description": "Invoice date in ISO 8601 format: YYYY-MM-DD"
      },
      "payment_terms_days": {
        "type": "number",
        "description": "Payment terms as an integer number of days (e.g. 30 for Net 30, 0 for COD)"
      },
      "line_items": {
        "type": "array",
        "description": "One entry per line item on the invoice",
        "items": {
          "type": "object",
          "properties": {
            "sku": {"type": "string", "description": "Earnventory SKU identifier"},
            "description": {"type": "string", "description": "Product description as printed"},
            "quantity": {"type": "number", "description": "Number of units"},
            "unit_price": {"type": "number", "description": "Price per unit in USD"},
            "line_total": {"type": "number", "description": "quantity × unit_price in USD"}
          },
          "required": ["sku", "quantity", "unit_price", "line_total"],
          "additionalProperties": false
        }
      },
      "invoice_total": {
        "type": "number",
        "description": "Sum of all line totals in USD"
      }
    },
    "required": ["supplier_id", "invoice_date", "payment_terms_days", "line_items", "invoice_total"],
    "additionalProperties": false
  }
}
```

Three things do the heavy lifting here:

**`required: [...]`** — Claude must include every listed field. If it can't determine the value, it has to make its best attempt rather than silently omitting the key.

**`additionalProperties: false`** — Claude cannot add fields beyond those defined in `properties`. No `notes`, no `confidence_score`, no `raw_text` — only what you specified.

**Typed, described properties** — `"type": "number"` means Claude won't return `"eighteen dollars fifty"` for `unit_price`. The description gives Claude the semantic signal it needs to map invoice content to the right field name.

When you combine all three, the schema eliminates most of the variance that causes downstream failures.

---

## Why This Works Mechanistically

Remember the core mechanism from Day 7: Claude generates one token at a time, each conditioned on everything before it. When Claude is generating a JSON object, the field names are tokens, and the schema provides high-probability anchoring for what those tokens should be.

When Claude sees a detailed schema in the tool definition:

1. **Field names are resolved before generation.** Claude doesn't have to choose between `items`, `line_items`, and `products` — the schema specifies `line_items`. The ambiguity that drove variance is gone.

2. **Types constrain the token space.** After generating `"quantity":`, the model knows the next token should be a number, not a string. The probability mass shifts toward numeric tokens.

3. **`additionalProperties: false` closes the door.** The model has been trained on JSON Schema semantics. This flag tells it the object must end at the defined properties. It won't attempt to add additional fields.

The insight: **you're not asking Claude to be more consistent — you're narrowing the probability space so that only valid outputs have high probability.** Inconsistency was never a model flaw; it was an underspecified prompt.

## Technique 2: Output Format Prompting

Strict tool schemas work when Claude is calling one of your tools. But what if you want Claude to return structured data directly in its message — no tool call, just text that your code will parse?

This is where output format prompting applies. The mechanics are simpler than schemas, but the discipline required is the same.

**Weak approach (what most people write first):**
```
You are an inventory analyst for Earnventory. Analyze the provided inventory data and give me a summary.
```

Claude will produce whatever format feels natural — sometimes a paragraph, sometimes bullet points, sometimes a table, sometimes JSON. Each run is different because there's no signal about what "correct format" means.

**Strong approach:**
```
You are an inventory analyst for Earnventory.

OUTPUT FORMAT — CRITICAL: Respond with a JSON object and nothing else. No prose. No markdown. No explanation. No code blocks. Just the raw JSON object, nothing before it and nothing after it.

The JSON must have exactly these top-level keys:
- "status": one of "ok", "warning", "critical"
- "affected_skus": array of strings (SKU identifiers with issues), empty array if none
- "summary": string describing the inventory state, maximum 120 characters
- "recommended_action": string describing what to do next, maximum 200 characters, "None" if no action needed

Example of a correct response:
{"status": "warning", "affected_skus": ["WN-001", "WN-007"], "summary": "Two SKUs below reorder threshold with 3-day lead time", "recommended_action": "Submit reorder for WN-001 (qty: 50) and WN-007 (qty: 20) before Friday"}

If any field value is unavailable, use null for that field rather than omitting it.
```

Four elements make this reliable:

1. **Explicit field names** — removes all ambiguity about what to output
2. **Value constraints** — enum for `status`, character limits for strings, explicit empty-array behavior
3. **A concrete correct example** — the model learns the exact pattern it should reproduce
4. **Explicit prohibitions** — "no markdown," "no code blocks," "nothing before or after" — you're closing off the most common escape hatches

## Common Failure Modes (and How to Fix Them)

Even with careful prompting, Claude will sometimes deviate. Here are the five most common failures and the fix for each.

---

**Failure 1: Markdown wrapping**

Claude outputs:
```
```json
{"status": "ok", "affected_skus": [], ...}
```
```

Your `json.loads(response)` gets a `SyntaxError` because of the backtick delimiters.

**Fix:** Add to your system prompt: *"Never use markdown code blocks. Never wrap output in triple backticks or `json` fence markers. Return raw JSON only, starting with `{` and ending with `}`."*

Also add a defensive fallback in your code:
```python
import re, json

def parse_structured(text: str) -> dict:
    # Try direct parse first
    try:
        return json.loads(text)
    except json.JSONDecodeError:
        # Extract JSON object from possible surrounding text
        match = re.search(r'\{.*\}', text, re.DOTALL)
        if match:
            return json.loads(match.group())
        raise ValueError(f"No valid JSON found in response: {text[:200]}")
```

---

**Failure 2: Trailing explanation**

Claude outputs:
```
{"status": "ok", "affected_skus": [], "summary": "...", "recommended_action": "None"}

I've analyzed the inventory data as requested. Let me know if you'd like more detail on any SKU.
```

`json.loads()` fails because of the trailing text.

**Fix:** Add: *"Your response must end immediately after the closing `}` of the JSON object. Do not add any explanation, closing remark, or text after the JSON."*

---

**Failure 3: Invented fields**

Claude returns fields you didn't define:
```json
{"status": "ok", "affected_skus": [], "summary": "...", 
 "recommended_action": "None", "confidence": 0.97, "analysis_timestamp": "2026-08-03"}
```

If you do strict key-access in your code, this passes through silently. If you validate against a schema, it fails.

**Fix:** In your tool schema, set `"additionalProperties": false`. In your format prompt, add: *"Output exactly these keys and no others: status, affected_skus, summary, recommended_action."*

---

**Failure 4: Numbers as strings**

```json
{"quantity": "12", "unit_price": "18.50"}
```

`unit_price * quantity` raises a `TypeError` — you can't multiply strings. Or worse, your database silently stores `"18.50"` as a varchar and your margin calculations are wrong for weeks before anyone notices.

**Fix:** In your schema, set `"type": "number"` explicitly for numeric fields. In your format prompt, add: *"Numeric values must be JSON numbers, not strings — write `18.50`, not `'18.50'`."*

---

**Failure 5: Optional fields silently omitted**

Your schema says `payment_terms_days` is required. On an invoice where payment terms aren't printed, Claude omits the field rather than guessing.

**Fix:** In your schema, include the field in `required` AND add to your description: *"If payment terms are not stated on the invoice, use `0`."* Give Claude a concrete fallback so it doesn't have to decide between omitting and guessing.

## When to Use Which Technique

| Situation | Technique | Why |
|---|---|---|
| Claude is calling a tool you defined | Strict tool schema | Schema is structurally enforced during generation |
| Claude returns data in its message | Output format prompting | No tool call to attach schema to |
| Deeply nested or complex structure | Tool schema (preferred) | Schema provides more precise type constraints at each level |
| Simple flat key-value output | Either — format prompting often simpler | Schema is overkill for 3-4 flat keys |
| Zero tolerance for parse failure | Tool schema with `additionalProperties: false` | Highest structural reliability |
| Changing requirements, rapid iteration | Format prompting | Easier to modify a system prompt than a schema definition |

## Earnventory Applications

Here's where structured output discipline pays off in concrete business terms for Earnventory:

**Invoice ingestion pipeline:** Your agent reads incoming invoice emails, extracts line items, and writes to your database. Without a strict schema, field name variance and type inconsistency produce silent data corruption — margins calculated on `"18.50"` instead of `18.50`, SKUs matched against `items[0].product_id` that sometimes doesn't exist. With a strict schema, the ingestion pipeline either succeeds cleanly or raises a parse error you can catch and flag for manual review. Both outcomes are better than silent corruption.

**Inventory health reports:** Your overnight agent scans all SKUs, flags anything below reorder threshold, and produces a structured report that feeds your dashboard. If the output structure is consistent, your dashboard code is simple: `data["affected_skus"]` always exists, always contains strings. If the structure varies, your dashboard either crashes or requires defensive code at every field access — technical debt that compounds.

**Supplier communication drafts:** Agent drafts responses to supplier emails and returns them as structured objects: `{subject, body, urgency_level, requires_review}`. The `requires_review: true` flag triggers a Slack notification to you before sending. This only works if the field name is always `requires_review` — not `needs_review`, `review_required`, or `flagged`.

**Margin analysis:** Agent analyzes price changes across a supplier's catalog and returns `{impacted_skus: [...], avg_margin_change_pct: ..., recommended_actions: [...]}`. The downstream code computes total exposure from `avg_margin_change_pct` — a type error here means wrong financial projections.

In each case, the pattern is identical: define the exact shape, provide an example, prohibit deviation.

## A Note on Model Reliability

Structured output reliability is not equal across the model tiers, and it's worth calibrating your expectations:

**Haiku 4.5** will follow format instructions on simple, shallow schemas. On complex nested schemas, it occasionally adds fields or slightly reshapes arrays. Needs extra reinforcement in the system prompt and a defensive fallback parser in your code.

**Sonnet 4.6** is reliable with clear format instructions and strict schemas. This is the right default for most Earnventory production use cases — reliable enough, affordable at scale.

**Opus 4.8** has the highest instruction-following accuracy. Worth the cost when you're parsing complex documents (multi-page contracts, ambiguous invoices) where format deviation would be hard to detect and expensive to correct.

The practical guidance: start with Sonnet + strict schema. If you're seeing 1–2% format failures in production testing, either improve the schema/prompt or upgrade to Opus. Don't start with Haiku for structured output unless you've validated it on your specific task.
